검토 결과, **네 모듈 모두 현재 형태가 즉시 “합성 불가능”한 것은 아닙니다.** 다만 `Pixel_Processer`는 실제 조합 경로가 매우 위험하고, `Pixel_Reader`는 Verilator가 조합 feedback으로 판단할 수 있는 구조입니다. `Decompresser`와 `Compressed_Data_FIFO`는 내부에 직접적인 조합 loop는 확인되지 않았습니다.

## 1. `Pixel_Reader.sv`

### 관련 경로

- `Pixel_Reader.sv:122-207`
- `Pixel_Reader.sv:288-574`
- `Pixel_Reader.sv:663-730`

주요 신호 흐름은 다음과 같습니다.

```text
fifo_r_state
    -> rgb_convert_req
    -> rgb_r_state
    -> rgb_convert_end
    -> fifo_r_state_next
```

동시에:

```text
valid_pixel_check
    -> RGB 변환 상태
    -> rgb_convert_end
```

### 판정

- `fifo_r_state`, `rgb_r_state`는 레지스터이므로 상태 전이 자체는 클럭으로 분리됩니다.
- 따라서 일반적인 상태 레지스터 기준으로는 명백한 조합 loop라고 단정하기 어렵습니다.
- 그러나 `rgb_convert_end`와 `valid_pixel_check`가 서로 다른 기능 블록에 있음에도 같은 조합 경로 분석에 포함되어 Verilator에서 다음 경고가 발생합니다.

```text
UNOPTFLAT: Pixel_Reader.sv:119
Signal: rgb_convert_end
```

Verilator의 경로는 다음과 같이 보고됐습니다.

```text
rgb_convert_end
 -> first always block
 -> valid_pixel_check
 -> RGB conversion always block
 -> rgb_convert_end
```

실제 논리식으로 보면 `valid_pixel_check`는 주로 `read_pixel_x`, `read_pixel_y`, `WX`, `WY`, `SCX`, `SCY`에 의존하므로 **진짜 직접 loop가 아니라 always 블록 단위 분석으로 인한 false positive 가능성도 있습니다.**

### 합성 위험

- 합성 가능성: **가능**
- 위험 수준: **Medium**
- 위험 내용:
  - 조합 블록 간 handshake 의존성이 복잡함
  - `rgb_convert_end`가 같은 cycle의 FIFO 상태 계산에 직접 사용됨
  - `Pixel_ready`가 조합식에 포함됨
  - 합성기마다 feedback 경고 처리 방식이 다를 수 있음

### 추가 기능 위험

`Pixel_valid`와 `RGB_reg_ready`는 `Pixel_ready`에 영향을 받습니다.

```verilog
if(RGB_reg_valid) begin
    Pixel_valid = 1;
    if(Pixel_ready)
        RGB_reg_ready = 1;
end
```

이 구조는 표준 ready/valid 프로토콜보다 강하게 결합되어 있습니다. `Pixel_ready`가 계속 0이면 해당 pixel 상태가 영원히 유지될 수 있습니다.

### 권장 구조

`rgb_convert_end`를 1클럭 register로 만들거나, 최소한 다음처럼 handshake를 분리하는 것이 좋습니다.

```text
RGB 변환 완료
    -> rgb_result_valid register
    -> FIFO가 다음 pixel 요청
```

즉, 조합 출력인 `rgb_convert_end`가 FIFO 상태를 직접 제어하지 않도록 해야 합니다.

## 2. `Pixel_Processer.sv`

### 관련 경로

- `Pixel_Processer.sv:345-365`
- `Pixel_Processer.sv:368-410`
- `Pixel_Processer.sv:443-830`
- `Pixel_Processer.sv:835-930`

Verilator가 보고한 경고는 다음입니다.

```text
UNOPTFLAT: Pixel_Processer.sv:271
Signal: layer_ready
```

추정되는 경로는 다음과 같습니다.

```text
layer_ready
 -> Pixel_Reader.Pixel_ready
 -> Pixel_Reader.Pixel_valid
 -> layer_valid
 -> z_input_valid
 -> z_input_ready
 -> layer_ready
```

### 핵심 문제 1: 조합 동적 배열 역매핑

```verilog
z_index_map[layer_z[i]] = i;
```

그리고 다시:

```verilog
z_input_valid[j] = layer_valid[z_index_map[j]];
```

마지막으로:

```verilog
layer_ready[z_index_map[j]] = 1;
```

이 구조는 다음 두 가지 역방향 매핑을 동시에 수행합니다.

```text
물리 layer -> z 순서
z 순서 -> 물리 layer
```

합성은 가능하지만, 10개 레이어에 대한 동적 mux 네트워크가 생성됩니다. 또한 `layer_z`가 중복되면 마지막 loop 대입이 이전 값을 덮어씁니다.

### 핵심 문제 2: valid/ready 조합 결합

```verilog
if(z_input_ready[1] == 1)
    layer_ready[z_index_map[1]] = 1;
```

각 `z_input_ready`는 다시 `z_input_valid`를 참조합니다.

```verilog
if(z_input_valid[1]) begin
    z_input_ready[1] = 1;
end
```

`z_input_valid`는 `layer_valid`에서 오고, `layer_valid`는 Pixel_Reader의 `Pixel_valid`에서 옵니다. 이 때문에 계층 전체를 합치면 조합 feedback처럼 보입니다.

### 판정

- 합성 가능성: **가능하지만 매우 위험**
- 실제 조합 loop 가능성: **있음**
- 위험 수준: **High**
- 가장 먼저 수정해야 할 모듈입니다.

Verilator의 `UNOPTFLAT`가 단순 false positive일 수도 있지만, 이 모듈은 실제로 `ready`가 `valid` 및 upstream 출력과 강하게 연결되어 있으므로 false positive라고만 보기 어렵습니다.

### 기능상 deadlock 가능성

메인 FSM은 모든 Z 단계가 valid가 되기를 기다립니다.

```verilog
if(Z1_valid && Z2_valid && ... && Z10_valid)
    Pipeline_move = 1;
```

그런데 각 Z 단계의 입력 valid는 Pixel_Reader가 내보내고, Pixel_Reader는 `Pixel_ready`를 기다립니다. 특정 레이어의 ready가 잘못 0이 되면:

```text
Pixel_Reader valid 대기
 -> Pixel_Processer ready 대기
 -> Pipeline_move 대기
 -> 다음 상태 전이 불가
```

상태가 영원히 진행하지 않을 수 있습니다.

### 권장 수정

가장 안전한 구조는 각 Z 단계에 1-entry register 또는 skid buffer를 넣는 것입니다.

```text
Pixel_Reader
    -> input_valid/input_ready
    -> Z-stage register
    -> next Z-stage
```

그리고 ready는 다음 규칙으로 제한해야 합니다.

```text
ready = !buffer_full || downstream_ready
```

`ready`가 현재 입력 `valid`에 직접 의존하지 않도록 해야 합니다.

또한 `z_index_map`은 조합 동적 배열 대신 다음 중 하나로 변경하는 것이 좋습니다.

1. `PPU_start` 시점에 정렬 결과를 레지스터에 저장
2. 명시적인 우선순위 mux 사용
3. z-order가 고정이면 물리적 연결을 직접 생성

## 3. `Decompresser.sv`

### 관련 경로

- `Decompresser.sv:160-180`
- `Decompresser.sv:171-320`
- `Decompresser.sv:456-590`
- `Decompresser.sv:763-850`

주요 흐름은 다음과 같습니다.

```text
decompress_state
 -> w_8_valid
 -> w_8_ready
 -> decompress_state_next
 -> 클럭
 -> decompress_state
```

### 판정

- 실제 조합 loop: **확인되지 않음**
- 합성 가능성: **가능**
- 위험 수준: **Medium**
- 주된 문제는 조합 loop가 아니라 handshake 정체 가능성입니다.

`decompress_state`는 레지스터이고, `decompress_state_next`는 다음 클럭에 반영됩니다. 따라서 상태 레지스터 경계를 우회하는 직접 조합 loop는 아닙니다.

### 위험한 handshake

```verilog
assign w_8_valid = ...;
assign w_8_ready =
    ((w_state == START) && (w_8_valid) && (...));
```

`w_8_ready`가 `w_8_valid`에 직접 의존합니다. 일반적인 ready/valid 규칙에서는 producer의 valid와 consumer의 ready를 독립적으로 만드는 편이 안전합니다.

현재 구조는 다음 문제가 있습니다.

```text
w_8_valid = 0
 -> w_8_ready = 0
 -> write FSM 진행 불가
 -> w_8_valid 생성 불가
```

이 조건이 특정 상태에서 발생하면 deadlock이 가능합니다.

### 추가 위험

`w_8_valid`는 조합식으로 생성되고, 실제 데이터는 순차 블록에서 저장됩니다. 따라서 다음 조건이 정확히 맞아야 합니다.

```text
w_8_valid && w_8_ready
```

그렇지 않으면 다음 문제가 생길 수 있습니다.

- pixel drop
- 같은 pixel 중복 저장
- `repeat_counter`와 실제 출력 개수 불일치
- 마지막 64비트 word 누락

### 권장 수정

```text
producer_valid = 데이터가 준비됨
consumer_ready = 저장할 공간이 있음
write_enable = producer_valid && consumer_ready
```

형태로 분리해야 합니다.

현재처럼 `ready` 계산 안에 `valid`를 포함하지 않는 것이 좋습니다.

## 4. `Compressed_Data_FIFO.sv`

### 관련 경로

- `Compressed_Data_FIFO.sv:327-470`
- `Compressed_Data_FIFO.sv:500-625`
- `Compressed_Data_FIFO.sv:625-760`
- `Compressed_Data_FIFO.sv:1020-1085`

### 판정

- 내부 직접 조합 loop: **확인되지 않음**
- 합성 가능성: **가능**
- 위험 수준: **Medium**
- 주요 위험은 외부 DDR3 handshake와 BRAM 시간분할입니다.

### BRAM 시간분할 구조

예를 들어 BRAM7은 여러 FIFO가 공유합니다.

```verilog
if(Universal_Layer1_dequeue ...)
    BRAM7_en_b = 1;

if(Universal_Layer2_dequeue ...)
    BRAM7_en_b = 1;

if(Script_Layer_dequeue ...)
    BRAM7_en_b = 1;
```

현재는 `clk_counter`가 one-hot처럼 동작한다는 가정에 의존합니다. 그러나 여러 dequeue 조건이 같은 cycle에 동시에 참이면 마지막 조건의 주소가 앞 조건을 덮어씁니다.

합성 자체는 되지만 다음 문제가 발생할 수 있습니다.

- 잘못된 FIFO 주소 읽기
- `BRAM7_read_state_next`와 실제 주소 불일치
- FIFO count와 front pointer 불일치

### DDR3 handshake

```text
EMEM_valid
 -> EMEM_ready
 -> EMEM_rdata
 -> BRAM write
 -> FIFO count 증가
```

이 모듈은 DDR3가 다음을 보장한다고 가정합니다.

- `EMEM_valid && EMEM_ready`에서 유효한 `EMEM_rdata`
- burst 응답 순서 보장
- `EMEM_ready`의 cycle 의미 고정
- burst 중 주소 자동 증가 또는 고정 주소 허용

이 계약이 외부 DDR3 컨트롤러와 다르면 조합 loop가 아니라 데이터 corruption이 발생합니다.

### 특히 확인할 점

`EMEM_r_counter`와 `tem_32_reg`를 이용해 32비트 두 개를 64비트로 합칩니다.

```verilog
BRAM9_din_a = {EMEM_rdata, tem_32_reg};
```

따라서 외부 DDR3의 read response가 한 cycle 지연되거나 `ready`와 `rdata`가 다른 cycle에 오면 word 순서가 깨질 수 있습니다.

### 권장 수정

- `EMEM_valid`와 `EMEM_ready`가 서로 조합적으로 의존하지 않도록 구성
- DDR3 응답을 별도 register에 저장
- `burst_data_valid` 신호 추가
- BRAM read 요청은 명시적인 one-hot mux로 구성
- 다음 assertion 추가

```systemverilog
assert ($onehot0({
    uni1_fifo_r_master,
    uni2_fifo_r_master,
    script_fifo_r_master,
    status_fifo_r_master
}));
```

BRAM7/8/9 각각에 대해 동시에 두 개 이상의 read request가 발생하지 않는지 검증해야 합니다.

## 최종 판정표

| 모듈 | 직접 조합 loop | 합성 가능성 | 주요 위험 |
|---|---:|---:|---|
| `Pixel_Reader` | 명백하지 않음, feedback 경고 발생 | 가능 | ready/valid 조합 결합 |
| `Pixel_Processer` | 실제 loop 가능성 있음 | 가능하지만 위험 | 동적 역매핑, ready feedback, deadlock |
| `Decompresser` | 확인되지 않음 | 가능 | `w_8_valid/w_8_ready` handshake 정체 |
| `Compressed_Data_FIFO` | 확인되지 않음 | 가능 | BRAM TDM, DDR3 burst 계약 |

## 우선순위

1. `Pixel_Processer`의 `layer_ready` feedback 분리
2. `Pixel_Reader`의 `rgb_convert_end`를 register handshake로 변경
3. `Decompresser`의 `w_8_ready`에서 `w_8_valid` 의존성 제거
4. `Compressed_Data_FIFO`의 BRAM TDM one-hot assertion 추가
5. DDR3 burst 응답 프로토콜을 명확히 정의하고 waveform 검증

현재 Verilator는 통합 lint에서 종료 코드 `0`을 반환하지만 `Pixel_Processer`와 `Pixel_Reader`에 `UNOPTFLAT` 경고를 내고 있습니다. 따라서 **문법적 합성 불가는 아니지만, 실제 FPGA/ASIC 합성 전에 이 두 feedback 경로를 반드시 구조적으로 끊는 것이 안전합니다.**
